# React Native / Expo conventions

This skill is the foundation for every other RN skill and agent. It does two things:
1. **Detects the actual stack** of the current project — never assume it.
2. **Defines conventions** to apply when the project itself has no stronger convention.

## 1. Detect the stack (always first)

Run the detector from the project directory (it walks up to find the RN package, and also handles monorepo roots):

```bash
node ~/.claude/skills/rn-conventions/scripts/detect-stack.js
```

If that path doesn't exist, the kit is installed per-project:

```bash
node .claude/skills/rn-conventions/scripts/detect-stack.js
```

If the session context already contains a "React Native project detected" summary (added by the kit's SessionStart hook) and you only need those fields, you can skip running the detector. Subagents start with a fresh context and always run it.

If neither works (no Node available), detect manually: read `package.json`, `app.json` / `app.config.*`, `eas.json`, `tsconfig.json`, and check for `ios/`, `android/`, `app/`, `src/`.

The report is read-only JSON. Key fields and what they decide:

| Field | Decides |
|---|---|
| `workflow` | Whether you may edit `ios/` / `android/` directly. In **CNG** (managed) projects, never edit native dirs — use app config and config plugins; native dirs are regenerated by `expo prebuild`. |
| `versions.expoSdk` / `versions.reactNative` | Which APIs exist. Check docs for that exact version before using a newer API. |
| `newArchitecture` | Whether libraries must support the New Architecture (Fabric / TurboModules). |
| `navigation` + `routerAppDir` | Where screens live and how routes are typed. |
| `state`, `serverState` | Where data lives. Don't introduce a second state library. |
| `styling` | How to style. Don't mix systems (e.g. no StyleSheet in a NativeWind codebase unless the project already does). |
| `testing` | How to write and run tests. |
| `i18n` | Whether user-facing strings must go through a translation function. |
| `packageManager`, `runCmd` | Which commands to run (`yarn` vs `npx` vs `pnpm exec` vs `bunx`). |
| `layout` | Where new files go, and which path aliases (`@/…`) to use in imports. |

## 2. Project conventions beat these defaults

Before creating anything, look at 2–3 existing files of the same kind (a screen, a component, a hook, a test) and **copy their patterns**: folder structure, naming, export style, how props are typed, how styles are declared. Also read `CLAUDE.md`, `README.md`, and lint config if present. The defaults below apply only where the project is silent.

## 3. Default conventions

**Language and types**
- TypeScript if `typescript: true`. No `any` — use `unknown` and narrow. Type props with a named `type XProps`.
- Prefer named exports for components and hooks. Exception: Expo Router route files **must** default-export the screen.

**Components**
- Function components only. Keep a component under ~200 lines; extract subcomponents and hooks.
- Logic in custom hooks (`useXxx`), presentation in components.
- No inline object/array/function props on hot paths (lists, frequently re-rendering parents) — hoist or memoize.
- `React.memo` only where profiling or list usage justifies it; don't blanket-memoize.

**Platform**
- Use `Platform.select` / `.ios.tsx` / `.android.tsx` for real platform differences; don't scatter `Platform.OS ===` checks.
- Respect safe areas (`react-native-safe-area-context`), never hardcode status-bar or notch heights.
- Test both platforms mentally: keyboard behavior, back button (Android), shadows (`elevation` vs `shadow*`), fonts.

**Lists and media**
- Long or dynamic lists: use `FlashList` if installed, else `FlatList` with `keyExtractor` and stable `renderItem`. Never `ScrollView` + `.map()` for unbounded data.
- Images: `expo-image` if installed (caching, placeholders). Always give explicit dimensions.

**Styling**
- Use the detected system. Colors, spacing and typography come from the theme/tokens file if one exists — no magic numbers or raw hex in components.

**Strings**
- If `i18n.libraries` is non-empty, every user-facing string goes through the translation function. No hardcoded UI text.

**Side effects**
- Every `useEffect` that subscribes, sets a timer, or starts a request must clean up / abort.
- No state updates after unmount; use `AbortController` for fetches.

**Native & dependencies**
- In Expo projects install packages with `npx expo install <pkg>` (picks SDK-compatible versions), not plain `npm install`.
- In CNG projects, native changes go through `app.json`/`app.config.*` and config plugins.

**Enforced by hooks** (if the kit's hooks are installed — a denied action is a rule, not an error to retry around)
- CNG projects: no edits in `ios/` / `android/`.
- Expo projects: packages only via `npx expo install`.
- `.env*` (except examples), signing keys and credentials: no reading or editing; Firebase config files only after user approval.
- Lockfiles and `node_modules`: never edited by hand.
- `eas build|submit|update`, cloud-changing `eas` commands and `git push` ask the user first; force-push is blocked.
- After each edit: formatter, linter and new type errors in that file are reported back.
- Before finishing: new type errors, failing related tests and leftover `console.log` / `.only(` / localhost URLs in lines you added are reported once. If something is intentional, say so and finish.

**Verification after changes**
Run what the project has (from `scripts`): typecheck (`tsc --noEmit` if no script), lint, and the affected tests. For Expo projects, `npx expo-doctor` catches dependency mismatches.
